# 2026-07-31

A long session on [[Beyond Bell Commander]]: office-Pi cache/version-drift cleanup, a full per-site branding system for the console and panel, a device-reboot action that surfaced a genuinely broken admin-login flow, and a multi-hour hardware investigation on [[Tablet Wall Panel]] that ruled out the camera for motion-wake and got the proximity sensor working instead.

## Office Pi cleanup: stale console build, a dark-mode contrast bug, PTT poll overhead

Started by chasing "the office Pi is still running the old UI" — server was serving the right files; it was the browser's own disk cache (no `Cache-Control` header on that route, same class of issue as 30 Jul's kiosk staleness). Along the way found and fixed a real one: `.pill.warn`-adjacent `--navy`/`--navySoft` chip text had no dark-theme "light" tier the way every *other* pale-chip family does (brass/blue/red/warn all correctly invert for dark mode; navy never did) — Add-sound/Add-zone buttons and the Bell Groups zone toggles were genuinely low-contrast in dark mode. Added `--navyText` and fixed six call sites.

Separately, "UI feels heavy, zone buttons flicker" turned out to be real and measurable: the panel's physical-PTT poll loop (`pollPTT()`, pre-existing) had never actually been running successfully on the office Pi — an earlier index.html/panel.js version mismatch was crashing `boot()` before it ever started. Fixing that inadvertently *woke up* a 10×/second fetch loop this kiosk's software-rendered Chromium had never had to sustain — measured 9.4% steady-state CPU from that loop alone (confirmed by stopping the agent and watching it drop under 1%). Eased 100ms→220ms (still well inside the agent's own 40ms/200ms debounce). Also fixed the zone-tile press animation not actually crossfading — `background` is a shorthand that includes `background-clip`, so overriding just `background` on the branding-override rule was silently resetting `text` clipping back to `border-box`, same footgun that later bit the Next-Bell countdown gradient too (see below).

## Per-site branding — console + panel

The real feature: one accent colour (+ optional secondary) now re-skins both apps per school, plus an uploadable logo. `Branding` model (`accent`, `secondary: str | None`, `logo_file`) on `SiteConfig`; a `branding.py` store (mirrors `media.py`'s shape, simpler — one logo, not a library); `/api/branding/logo` upload + reset, served back via a `/branding-assets` static mount. Colour derivation is ported identically into the console (React, `bell-commander-app.jsx`) and the panel (plain JS, `panel.js` — separate apps, no shared build step) — grounded in the *real* hand-tuned tokens' measured HSL ratios rather than guessed: light-theme Pale/Edge sit at ~96%/~86% lightness of the same hue, dark-theme Deep is the base colour unchanged, dark-theme brass is the base lightened for a dark background, etc. Never touches `--red` — alert/danger colours stay universal regardless of a school's palette, a deliberate safety call.

Testing the derivation (a genuine changeover to Concord High School's real palette — deep green `#295E51` + gold `#FFD36D`, crest logo uploaded through the real API, not faked) surfaced a string of real, previously-invisible bugs, all from things that had Beyond's own blue/amber hardcoded instead of reading the token system:
- `.btn.primary` (and the panel's Talk button, and its zone-tile selected state, and its `.btn.primary`) — hardcoded gradient stops, only ever exercised as Beyond's own blue until something tried a different accent.
- Focus rings, calendar day/month selection, the day-spine "now" cursor's pulse, the "hot" Next-Bell ring's glow — all hardcoded `rgba(40,112,255,…)`. Added a `--brass-rgb` token (light/dark, plus the branding override emits it) and swept every hardcoded occurrence to it.
- The header's aurora gradient's *base* layer was hardcoded navy-black regardless of accent — a branded header still washed out to Beyond's own near-black at the edges rather than a dark tint of the school's own hue. Retinted from the accent's own hue at reduced saturation (very dark colours read as muddy at full chroma, same reasoning the hand-tuned Pale tokens already use).
- The Next-Bell countdown's gradient (`brass → red`) is a deliberate Beyond-brand two-tone (blue + magenta, "the two BNS brand voices") that reads as "the timer is fading into an alarm" for any *other* accent. Swapped red for the secondary colour when set, else a same-hue brassDeep shade — never alert-red for a branded site. Building this one also caught the same `background-clip` shorthand footgun as the zone-tile fix above: the override rule needs to repeat `-webkit-background-clip`/`background-clip`/`color`, not just `background`, or the clipped-to-text gradient silently becomes a solid box (the numbers vanish entirely — this one made it to a screenshot before being caught).
- Panel had its own version of all of the above (`--brass-rgb` missing from its branding override entirely, plus two hardcoded amber glows) — same fixes, ported.

Console Zones page also gained a real Inside/Outside badge per zone (reusing the existing `zone.kind`, which the panel already showed but `/api/config` never actually sent to the console — a second real, separate bug, not just a missing UI element). Setup → Branding card: accent + secondary colour pickers, logo upload/reset, live preview.

## Device reboot + a real admin-login bug

Added "Reboot device" next to the existing service-restart on the System page (`system.reboot_device`, same fire-and-forget-after-a-delay shape as the existing `restart_appliance_service`, its own confirm dialog spelling out that this is a full host reboot — longer outage, network drops — not just the appliance service). Testing it surfaced a real, previously-uncovered bug: `admin_login`'s `not admin_password or not compare_digest(...)` rejected *every* login attempt whenever `BC_ADMIN_PASSWORD` was unset — which is the documented default ("no gate"), and is the office Pi's actual real-world state. The `not admin_password` half alone always made the `or` true, so the Unlock button had been permanently unreachable on any install that never configured a password, even though `require_admin` itself was correctly gating nothing in that state. Fixed to mirror `require_admin`'s own rule; added `tests/test_admin_auth.py` (6 cases) since this had zero prior coverage. 437 tests passing, committed as two commits on `feature/ux-audit-fixes`, deployed to the office Pi.

## Tablet: camera ruled out, proximity sensor wired up

Full technical write-up in [[Tablet Wall Panel]]. Short version: tried the onboard camera for wake-on-approach first — raw Bayer stills show a strong, stable ~33% frame-diff noise floor with nothing moving (almost certainly lighting flicker against a long fixed exposure, no anti-flicker control on this sensor driver), and two live tests with a real person walking up to the lens, correlated second-by-second, showed zero signal above that noise regardless of resolution. A genuine dead end, proven rather than assumed.

Pivoted to the proximity sensor (STK3311, previously only logged as "works" with no detail) — found three real bugs before it did anything: the kernel driver never actually enables PS mode on this bare Linux install (nothing calls the ioctl an Android HAL normally would), the first correlated register test used the wrong FLAG register address *and* only read half of the 16-bit PS_DATA value (LSB, missing MSB), and the final daemon then hit `EBUSY` from the polite `I2C_SLAVE` ioctl (needed `I2C_SLAVE_FORCE`, since the kernel driver already owns that address). Once all three were fixed: baseline ~130, climbing past 1000 with a hand 2-5cm away, clean and repeatable. `motion-wake.py` deployed as a systemd service, verified fully live (screen forced off, real approach, watched the log cross the threshold, confirmed via `xset q` that the monitor actually came back on).
