# 2026-07-30

Continuing straight on from [[2026-07-29]]'s hardware session on [[Tablet Wall Panel]] — a schematic arrived overnight for the tablet's rear I/O terminal, which unparked the GPIO investigation that had been shelved since 22 Jul. Turned into a full day: the physical switch working end-to-end, a kiosk reliability fix found by the same testing, and a real DSP config regression on the office Pi ([[Xilica Solaro Driver]]) exposed and fixed along the way.

## Schematic decode and the pull-up fix

A crop of the "GND / 1 / 2" rear terminal gave `GPIO0_B4` = `GPIO01` and `GPIO0_D3` = `GPIO02` — decoded to **gpiochip0 line 12** and **line 27** (RK numbering `bank*32 + group*8 + index`). Both confirmed unclaimed on the live device, sitting at chip power-on defaults. The circuit is a bidirectional SK3018 level shifter per terminal (100R series to the SoC side, 10K pull-up to 5V on the outside), so each terminal is a 5V open-drain dry-contact input.

Both lines read `0` under every bias mode regardless of wiring — the real blocker. `pinconf-pins` showed the RK3576 boots these pins with an internal pull-down that fights the board's pull-up and parks the pin in the indeterminate band; libgpiod's `-B pull-up` request was accepted by the kernel but never reached the actual hardware register. Fixed with a direct IOC-GRF write, the offset derived from the mainline `pinctrl-rockchip.c` source rather than guessed — bank 0's pull config turns out to be split across two distant register offsets, which is exactly why a naive contiguous scan would never have found it. Verified against all 32 bank-0 pins' known bias states before trusting the encoding. Wrapped in a boot-persistent `io-terminal-init.service`.

**One real incident**: before deriving the offset from source, a blind register sweep across the IOC/PMU GRF address space hung the tablet hard enough to need a physical power cycle (ping failed, ARP went `FAILED`, SSH and ADB both dead). Recovered cleanly (journal replay, self-healed) but it's now a hard rule for this board: reading an unimplemented or gated register can stall the bus as badly as a bad write — never sweep, always derive the exact offset first.

Full technical write-up in [[Tablet Wall Panel]].

## Push-to-talk, built and verified live

With the terminal readable, built `ptt-agent.py` — a root daemon on the tablet (same shape as `netpanel.py`/`led-panel.py`) that runs `gpiomon` on line 12 and debounces it with asymmetric hysteresis (40ms to engage, 200ms to release), tuned from a real bounce capture on the actual switch. `panel.js` polls it over loopback and calls the exact same `startTalk()`/`stopTalk()` the on-screen Talk button uses — no synthesized touch, no dependency on button position, silent no-op on any deployment without the hardware.

Verification took a few honest misses before it stuck: a plain browser reload served Chromium's heuristically-cached old `panel.js` (no `Cache-Control` header on that route), so the new poll loop simply wasn't running yet — a hard reload (`Ctrl+Shift+R`) fixed it, confirmed by temporarily logging requests to the agent. After that, a real sustained hold drove the *engine's own* `/api/status.paging` field live for the full duration and dropped cleanly on release — proof the whole chain works, not just the local daemon.

## Kiosk discovery race, found by the same testing

The tablet and its Bell Commander had both been power-cycled around the same time, and the kiosk's `boot()` gave up to the manual picker after a single failed LAN-discovery check — "Nothing found automatically." Since the discovery mechanism itself was fine moments later, `boot()` now retries for up to ~45s before giving up, still with no hardcoded fallback address (explicit instruction: keep it dynamic). Also swapped the countdown bar's `width` animation for `transform: scaleX()` while in there — a real perf fix given this SoC's known headroom issues, caught by the design-review hook.

## Xilica DSP regression, found by PTT's own test traffic

Heavy polling during PTT verification wedged the office Pi's engine completely — `/api/status` itself stopped responding, and `systemctl restart` needed a `SIGKILL` after a 90s graceful-stop timeout. Root cause: `device.json`'s `dsp_host` had regressed to `192.168.1.210`, a *different site's* bench Solaro, unroutable from the office LAN — and that deployment predates the 26 Jul connect-timeout circuit breaker, so every request against the dead address could hang indefinitely rather than failing fast.

Fixed via the supported API (`PUT /api/system/driver`, then `PUT /api/system/sound` to align the stale `ahm_host` too), restarted clean, verified `online: true` and the panel showing "Sound system online." Backed up the now-fully-consistent `device.json`. **The circuit breaker itself is still not deployed to that box** — the address is right now, but a future DSP outage there will hang the same way until that file is ported. Full detail in the new [[Xilica Solaro Driver]] reference note, which also consolidates the driver's config precedence rules and known-bug history that had been scattered across several days' journal entries.
