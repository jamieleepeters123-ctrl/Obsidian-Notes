# Beyond Bell Commander

Productised school PA + bell scheduling system under the BNS brand.

## Architecture v2 (locked — Jul 2026)
Designed from scratch for maintainability and stability. Three lines:
**Headless Linux appliance (engine) → TCP :51325 → AHM (playback + Dante routing) → per-block amps.** Any browser is the face.

### Head end
- Headless Pi / Linux appliance in the rack beside the AHM. No attached display — a dead screen is cosmetic, never a bells fault. Easy swap via golden image + site config.
- **One Python service**: scheduler, AHM driver, EVAC GPIO, phone-home client, serves the UI. FastAPI + SQLite (WAL). Deliberately boring, few pinned dependencies.
- **Scheduler = compiled tick loop, not a framework.** Daily (and on config change) the engine compiles the day's plan into a flat list ("ring bell X to group Y at 11:00:00"); a 1-second tick executes it. ~100 readable lines, exhaustively unit-tested: every 2026 date, every override, DST. "Did we break bells?" is a CI answer.
- **Fake AHM** test server (speaks the documented protocol) — full schedule→driver→DSP path exercised on every commit, no hardware. Field bugs reproduced + pinned as regression tests.
- Stability layers: Pi hardware watchdog → systemd → app self-check; read-only rootfs; no auto-updates (deliberate tested release images); chrony; fully functional with zero internet (telemetry queues locally).
- Config = one schema-validated JSON. Code / config / data never mix. Reflash + config.json = site restored.

### Displays (fully decoupled — all just browsers on the appliance URL)
- Office PC / iPad — zero cost
- ELC SMT101 10.1" Android wall panel (Fully Kiosk) — the 10" upgrade AND the Android-tablet option in one SKU (see [[ELC Smart Panels]])
- Pi + 7"/10" touch all-in-one where a single-box look is wanted (PiFace kiosk pattern)

### Audio
- **AHM-16** (product floor): internal WAV bell player (~2.5 GB storage), matrix, priority ducking. Driver = documented TCP :51325 (ahm_player.py groundwork).
- **Dante I/O card** → decentralised Dante amps per block → local 100V speakers. One network drop per block; block failure silences only that block. Netgear M4250 (IGMP, PTP QoS).
- **Music bells** (schools change songs each term, self-service): Audinate AVIO USB on the appliance puts it on Dante as a source. Staff upload MP3 in UI → ffmpeg normalise/trim/fade → assign to any bell. Engine health-checks the path and falls back to AHM stored tone automatically. (Music licensing = school's responsibility; APRA AMCOS education licences generally cover NSW schools.)
- **Fallback bells**: AHM **Manage > Events** scheduler (50 events/config, NTP-synced, Track Playback event type) holds a dormant mirror of the core timetable. Activation via labelled SoftKey or remotely. Bells survive appliance failure with no extra hardware. *(Algo 8301 removed from plan — AHM Events does its job for free.)*
- No file upload to AHM over documented TCP — uploads ride AH-Net (System Manager). Product answer: fixed sound-slot bank loaded at commissioning + UI remaps slots; true uploads = remote System Manager support task. Music bells cover the "custom audio" demand anyway.

### Safety
- FIP dry contact (N/C) → appliance GPIO → holds all bells. Supplementary only — certified EWIS (AS 1670.4) always independent and untouched.
- EVAC events logged forever (see [[Bell Commander Telemetry]]).

### Remote management (decided)
- Outbound-HTTPS phone-home → office-hosted Docker portal (fixed IP; confirm contractually static). External uptime watchdog + UPS non-negotiable. VPS migration = DNS change.
- Remote access: 4G out-of-band gateway w/ Tailscale on rack side; school-network Tailscale only with written IT approval.

### Languages
- **Python** everywhere on the backend (appliance service + portal, one monorepo, shared models) — matches existing BNS tooling (Flask, ReportLab, ffmpeg, ahm_player.py).
- **React** UI (Schoolyard), built to static files, vendored per release — no build tooling on the Pi.
- Node-RED = bench/prototyping tool only, never in the shipped image.

### Engine (hardware-free core, ~78 tests, "did we break bells?" is a CI answer)
- `compile_day(config, date)` → sorted bell list or a silent reason. Gating: **no-bell date → special day → weekend → out of term → template**. (A *special day* = per-date template; forces a ringing day, overriding weekend/holidays — fixed 8 Jul after it silently no-showed out of term.)
- `Engine.tick(now)` — 1-second loop, fires each bell once inside a grace window (never rings a stale bell after a restart), EVAC/silence/skip/manual overrides, recompiles at midnight, DST-correct via `zoneinfo`.
- `SiteConfig` = one pydantic-validated JSON (zones, groups, sounds, day templates, calendar). Bad references fail at load.
- **AHMDriver** — persistent Ext-Control TCP :51325 (play SysEx, mute, level, get-level heartbeat, get-name). Fails soft, never crashes the tick loop. **FakeAHM** speaks the same protocol → the whole schedule→driver→AHM path is tested with no hardware. Real office AHM replied to get-level in MIDI *running status* (7-byte, not 9) — driver fixed to accept it.
- Audit log = **SQLite (WAL)**, every ring / skip / hold / EVAC / manual, UTC at source.
- **FastAPI** wraps it (blocking tick runs in an executor thread) and serves the Schoolyard React UI.

### UI (Schoolyard React, served from the appliance)
Tabs: **Today** (live countdown, chalkboard timeline, Ring/Skip/Silence/EVAC), **Calendar** (year view from the real calendar), **Zones** (live mute — switch goes red when muted), **Log**, **Setup** (commissioning), **System**.
- **Setup** sub-tabs — School / Sounds & Zones / Timetable / Calendar — with one Save that validates and **hot-reloads live** (a bad edit is rejected, running config keeps ringing).

### Commissioning = "point at the AHM + the DoE"
All importers fetch *candidates for review*, then save through the validated config write.
- **Bell sounds ← AHM library** (AHNet :51321 track list). Office AHM: Period_Bell, Lock_Down, Lock_In, EVAC, All_Clear, Shelter-in-place.
- **Zones ← AHM zone names** (Ext-Control get-name). Office AHM: Gym, Canteen, Kiss&Ride, B/C/D Block Int/Ext (ch 1-8). Renaming a zone + Save **writes the name back to the AHM** (AHNet name-manager → shows in System Manager). Each zone carries an "AHM ch" so mutes/routing hit the right output.
- **Timetable ← the school's bell-times page** (restricted to `schools.nsw.gov.au`). Parses the DoE CMS layout; times reliable, labels reviewed.
- **Term dates ← NSW DoE calendar** (`education.nsw.gov.au/schooling/calendars/{year}`, Eastern/Western). **Public holidays ← NSW** (Nager.Date, filtered to NSW), now with the holiday *name* stored per date.

### System settings
- **Network**: DHCP/static via NetworkManager with a **90 s auto-revert safety** (a bad static IP can't lock out a remote appliance); MAC shown.
- **Display**: brightness + **sleep timer** (blank after N idle minutes, wake on touch) on the DSI panel; backlight is `pi`-writable, an X-side `xprintidle` watcher does the blanking.
- **Time**: **custom NTP server** (systemd-timesyncd drop-in), with clock-sync status shown — silent drift = broken bells.

- **17 Aug (correction): remote paging DOES work off-subnet — the mDNS half of the cross-VLAN analysis was wrong.** Prompted by a one-line observation ("im connected to the office over a vpn and the paging works") that contradicted the morning's answer — and which the morning's own evidence should already have flagged, since **every Playwright verification that day ran from a VPN client, off-subnet, and connected fine**. Measured it properly instead of re-arguing: instrumented the real `/mobile` page to dump `getStats()`' selected candidate pair, from a VPN client at `172.16.240.2` against the appliance at `172.16.200.217` — different subnets — and got `LOCAL type=host 172.16.240.2:56477` ↔ `REMOTE type=host 172.16.200.217:48607`. A **direct host-to-host UDP flow, no relay**, and critically a **real IP in the local candidate, not a `.local` name**.
	That kills the mDNS reason outright, and for a structural reason worth writing down: Chrome only substitutes an mDNS hostname for a host candidate when the page **lacks media permission**. The paging page can't function without mic permission, and `mobile.js`'s `startTalk()` awaits `getUserMedia` *before* it constructs the `RTCPeerConnection` — so permission is always already granted by the time candidates are gathered, and Chrome publishes the real address. The mDNS path is structurally unreachable in this application, so `aioice`'s inability to resolve it across a VLAN simply never arises. (And even if it did, `aioice/ice.py:812-839` implements RFC 8445 §7.2.1.3 peer-reflexive learning — it recovers the peer's address from the source of an inbound STUN check regardless of what the SDP claimed. That nuance was itself a first, partial correction before the measurement settled it properly.)
	So the real picture is **one** constraint, not two: same-VLAN works, any routed path that doesn't filter UDP works (the VPN, confirmed), and only a properly segmented VLAN with a real ACL fails — because `aiortc` binds an ephemeral UDP port (`:48607` above) with no `port_range` in this `aioice`, leaving nothing to write a firewall rule against short of "allow all UDP". The parked TURN plan is still the right fix *for that specific case* and its file has been corrected accordingly, but it's now clearly **not urgent**, since the access path actually in use works today. Lesson worth keeping: the disconfirming evidence was already sitting in the day's own test logs, and reading the library source felt rigorous enough to skip measuring the thing itself.

Verified the whole chain rather than the endpoints alone — netpanel serves the launcher with the real token injected and the `innerHTML` sink gone, the kiosk restarted and landed on a window titled "Beyond Bell Panel", Chromium's own cookie jar holds a persistent `bc_panel` for the engine host, and a screenshot confirmed the panel renders correctly (zones with INSIDE/OUTSIDE badges, today's spine, Talk button, Ready/Busy lamps, wallpaper branding, next bell 08:05). The XSS clamp was tested against a **genuinely hostile responder** — a throwaway UDP script on the panel answered the discovery broadcast with `<img src=x onerror=alert(1)>`, embedded `\x00`/`\x07` bytes, 200 padding chars and `http_port: "; rm -rf /"` — control bytes stripped, name truncated to 64, port coerced to `80`, and because the real engine answered too this reproduced the genuine two-engine `showMultiple()` render path rather than an approximation. Two tooling gotchas for that device recorded in [[Tablet Wall Panel]]: no `sqlite3` binary (read Chromium's cookie DB via `python3` against a *copy*, it's locked) and no `ffmpeg` (the 12 Aug `xwd`→png recipe fails; pull the `.xwd` and convert locally with PIL).

	**v0.4.0 cut and tagged** (17 commits since v0.3.3, which predated the whole remote-paging feature) — a minor bump rather than a patch, since it carries a new subsystem, a persisted-config schema change, and six security fixes. Pushed to both remotes, **not published to the portal**: the panel-token fix is a two-device change, so any appliance self-updating its engine without its tablet in the same window would have its wall panel's EVAC/paging buttons start 401ing — that warning leads the release notes rather than sitting buried in commit titles. `./release.sh --publish-only 0.4.0` when each site's tablet can be done alongside.
	**The cut itself exposed a latent bug in `release.sh`.** It logged "updating CHANGELOG.md (since pre-turn-relay-2026-08-17)" — `git describe --tags --abbrev=0` returns the nearest reachable tag *by topology regardless of name*, so the two rollback-point tags created this week (`pre-remote-paging-2026-08-12`, `pre-turn-relay-2026-08-17`) shadowed the real release tags. The v0.4.0 entry was generated from the wrong baseline and listed **2 commits instead of 17**, omitting the entire feature the release is named for. Fixed with `--match "v*"` (the only tag shape that marks a release here) and the entry rewritten with the full range — as a **follow-up commit rather than by re-tagging**, since v0.4.0 was already on both remotes and moving a published tag to fix documentation is the wrong trade. Latent since the `pre-*` convention was introduced on 12 Aug: any future non-release tag would have silently truncated the next changelog the same way. v0.3.3's entry predates those tags and is unaffected.

- **18 Aug (pm): a RaspiAudio 8xOUT sound card commissioned, and Wi-Fi setup built into the System page — where the first real connection attempt exposed a WPA3 trap and a bug in my own scan code.** The new card turned out **not** to be a HifiBerry despite appearances: its HAT EEPROM reads `product: 8xOUT, vendor: Raspiaudio.com`, and it identifies as DAC8x-compatible so the stock in-kernel `snd_rpi_hifiberry_dac8x` overlay drives it (same vendor as the RaspiAudio Ultra in the Pi Zero station plan). **No drivers were needed** — driver loaded, EEPROM auto-detected, ALSA card 2, 8 outputs. Two log lines that read as faults but aren't: `no ADC8x detected` is the overlay probing for the optional ADC add-on that isn't fitted, and `Subdevices: 0/1` just means the engine holds the stream open. The channel config had already been moved to **discrete outputs 0/1/2/3** (they doubled up on 0/1 that morning), so bells and WebRTC paging no longer share a wire, with four channels spare. Applied the five Debian-Security updates only (`libgd3`, `libnss3`, `p7zip`, `p7zip-full`, `unzip` — simulated first: nothing removed, no kernel pulled in), deliberately holding back kernel 6.12.96 and `rpi-eeprom`, which need a reboot and are the ones that could disturb the sound driver. On request, made the 8xOUT the **system default** via a new `/etc/asound.conf` referencing it **by card name (`sndrpihifiberry`), not index** — ALSA card numbers are assigned in probe order and shift when a kernel update or added device reorders them, and "default silently became HDMI" is the wrong failure for a bells appliance. Proved it using the engine's own lock as the oracle rather than asserting it: `aplay -D default` returned **"Device or resource busy"** (the card the engine already holds) while `hw:vc4hdmi0` returned a *different* error entirely. Worth remembering — `aplay -L` in an SSH session reports `default` as PulseAudio, because interactive logins start Pulse and it shadows the config; **the service has no Pulse and enumerates raw ALSA**, so the two contexts genuinely differ and a shell test alone would have misled. A 1s 880Hz test tone at 30% then measured **−20.9 dBFS** on the bells channel, exactly the arithmetic (0.3 generator × 0.3 volume = 0.09 → −20.9), with the other three channels flat at −80 throughout — confirming the new card's channel separation, which the morning's shared-output config could not have produced.
	Then **Wi-Fi setup on the System page**, since the appliance could previously only be put on a network by wired config — no Wi-Fi support existed anywhere in the engine, even though the wall panel's own `netpanel.py` has been driving nmcli on real hardware since July. Ported that rather than reinventing it, carrying across three fixes it had already paid for: the `--` argv terminator (an SSID starting with `-` must not parse as a flag), the "started from disconnected" revert case, and treating nmcli's terse output as escaped — it emits a literal `:` inside an SSID as `\:`, so a naive split corrupts legitimate network names. **One revert timer, not two**: a Wi-Fi join arms the *same* timer `apply_network` uses and is confirmed by the same `/api/system/network/confirm`, because two independent auto-reverts against one appliance could fire against each other and undo a change the operator had already confirmed. `wifi_status()` reports three states apart — no adapter / radio off / radio on but nothing in range — since they need different actions and one empty list for all three reads as broken hardware. The Pi was the middle case: adapter, firmware and `country AU` regulatory domain all fine, radio simply soft-blocked, so the page offers to turn it on. Deliberately did **not** reuse `system.py`'s own `_run()` helper: its 5s timeout is far too short for a rescan (~20s) or connect (~50s), and it collapses every failure into `""`, which would make "no adapter" and "nmcli crashed" indistinguishable — added `_run_rc()` alongside it.
	**The first real connection then failed, and the cause was not what the error said.** `BNS-WLAN` runs in **WPA2/WPA3 transition mode** (RSN flags literally `psk sae`). NetworkManager sees both and picks the stronger — SAE/WPA3 — but the Pi's `brcmfmac` firmware doesn't implement SAE, and the failure surfaces as **"Secrets were required, but not provided"**, which points squarely at the password. It wasn't the password: the profile left behind by the earlier attempt already held the correct PSK (verified by comparison). Pinning `key-mgmt` to `wpa-psk` with `pmf=optional` — the WPA2 the same AP also offers — associated immediately. **Fixed in the product, not just on the box**: `wifi_connect` now detects the leftover `key-mgmt=sae` profile after a failed join and retries as WPA2-PSK, gated so an ordinary wrong password still fails honestly rather than being papered over. Transition-mode APs are increasingly the default on modern gear, so every future site would have hit this same dead end with the same misleading message.
	The live test also caught **a genuine bug in my own scan code**: `BNS-WLAN` has four APs, nmcli emits one row per BSSID, and only the associated one carries `ACTIVE=yes` — my dedupe kept the first row and silently dropped that marker, so the page named the right network at the top while showing nothing as connected in the list below. Now merges duplicates (connected if any BSSID is, strongest signal wins). Neither bug was reachable from the mocked tests; both needed real hardware with multiple access points. Final state: `wlan0` on `172.16.200.190/24`, **eth0 still primary at metric 100 and wlan0 a backup at 600** — both on the same subnet, so Wi-Fi is now genuine redundancy rather than a replacement; if the wired drop fails the appliance stays reachable. 743 tests (was 722 at the start of the day), commits `c1307f3` and the follow-up fix, deployed and verified live. **One self-inflicted mistake worth recording**: the Wi-Fi dropped once mid-verification because the first safety timer I armed had no cancellation mechanism (a plain `sleep 150` then disconnect) and fired *after* the connection had already succeeded — the journal named it exactly (`op="connection-deactivate" uid=0 reason='user-requested'`). The second one I armed was cancellable via a sentinel file and behaved correctly. Lesson: an unconditional background timer is not a safety net, it is a scheduled outage.
